# v1.4 Epic Skin Polish - Milestone Brief

**Purpose:** Prepare the follow-up milestone that polishes epic skins A, B, and
C after v1.3 implementation work finishes.

## Why This Milestone Exists

v1.3 established structurally distinct skins. The next step is not more concept
work; it is disciplined iteration:

- review each skin visually across all pages and breakpoints
- check each skin against the v1.0 requirement floor
- fix all non-nitpick issues found
- stop only when the skin looks clean or a hard iteration cap is reached

This follow-up exists so the skin agents do not have to carry shared planning
and repo housekeeping on top of their concrete design-fix work.

## Tooling Constraint

The current GSD milestone parser only recognizes milestone versions in `vX.Y`
form. Because of that, this follow-up is prepared as **v1.4** rather than a
literal `v1.3.1`, even though it is conceptually a decimal follow-up to v1.3.

## Core Goal

Bring all three epic skins to review-ready quality through bounded iterative
visual + requirements loops, while keeping shared repo/planning housekeeping out
of the skin-specific execution phases and preserving the established
one-branch comparison model.

## Comparison Model

- one branch contains all reviewable versions
- `site/epic/a/`, `site/epic/b/`, and `site/epic/c/` remain the canonical
  implementation directories
- a shared start page/version picker is the canonical human entry point for
  comparison
- shared phases own that picker/review surface; skin phases own only their
  directory-local polish work

## Shared Constraints

1. Browser-driven audit work is **sequential only**. The local browser is a
   shared bottleneck, so A, B, and C cannot run in parallel during visual audit
   phases.
2. The one-branch, pick-your-version-at-the-start review flow must remain
   intact.
3. The v1.0 requirements remain the compliance floor:
   `.planning/milestones/v1.0-REQUIREMENTS.md`
4. Review all eight pages at `375px`, `768px`, and `1280px`.
5. Every audit pass produces a written TODO list before fixes start.
6. Fixes for one audit pass should be batched, not split into one execution per
   small issue.
7. Stop condition per skin:
   - clean pass with no further obvious issues, or
   - 5 iterations reached, then pause for user decision
8. Skin-specific phases should stay inside their own `site/epic/{a|b|c}/`
   directory unless they hit a blocker that is explicitly shared.

## Milestone Scope

### Shared Prep

- confirm A/B/C directory inventory and live-review paths
- align docs with actual repo state
- define the canonical shared start page/version picker contract
- document comparison/publish expectations and version labels

### Skin-Specific Work

- sequential polish loop for Design A
- sequential polish loop for Design B
- sequential polish loop for Design C

### Close-Out

- comparison-ready review surface with shared start page/version picker for
  owner handoff

## Proposed Phase Structure

- **Phase 32: Polish Baseline & Review Surface**
  Shared housekeeping, inventory verification, path sanity, and review-surface
  preparation, including the shared picker contract.
- **Phase 33: Epic Skin A Polish Loop**
  Audit -> TODO -> fix -> verify for `site/epic/a/`.
- **Phase 34: Epic Skin B Polish Loop**
  Same process for `site/epic/b/`.
- **Phase 35: Epic Skin C Polish Loop**
  Same process for `site/epic/c/`.
- **Phase 36: Comparison Publish & Review Pack**
  Ensure all three skins are easy to review from the shared start page/version
  picker and that publish/review instructions are explicit.

## Requirements To Carry Into The Milestone

- shared baseline/housekeeping requirements
- audit-loop requirements common to all three skins
- one review-readiness requirement per skin
- comparison/publish readiness requirements
