## What Happened in v1.2

v1.2 "ClaudesDesigns" produced 3 design directions (A, B, C) across Phases 20-23. All three are **complete and production-ready** on their respective git branches (`design/a`, `design/b`, `design/c`).

**The problem:** All three designs are "chromas" (recolors), not "epic skins" (structurally distinct designs).

### Evidence — What's identical across all three designs

| Aspect | Design A | Design B | Design C |
|--------|----------|----------|----------|
| Homepage section ordering | hero → gate → 2col → 3col → CTA | hero → gate → 2col → 3col → CTA | hero → gate → 2col → 3col → CTA |
| Hero composition | Centered h1 + subtitle + CTA | Centered h1 + subtitle + CTA | Centered h1 + subtitle + 2 CTAs |
| Copy | ~95% identical text | ~95% identical text | ~95% identical text |
| Information architecture | Same content, same order | Same content, same order | Same content, same order |
| Nav pattern | Sticky top bar + hamburger | Sticky top bar + hamburger | Sticky top bar + hamburger |
| Page structure | Same sections per page | Same sections per page | Same sections per page |

### What actually differed (surface-only)

- Color tokens (navy/amber vs teal/white vs terracotta/cream)
- Font families (Playfair+Inter vs Outfit vs Nunito+DM Sans)
- Container treatment (separator lines vs color bands vs rounded cards)

### Root cause

The Phase 20 design directions document (`20-DESIGN-DIRECTIONS.md`) specified colors, fonts, hero copy, and container styling — but the **page skeleton was never varied**. All three directions were built on the same HTML structure with different `@theme` blocks and container classes.

### User verdict (Phase 24 review)

> "Not enough own identity. If the designs were Champion Skins in League of Legends they would be simple recolors, we were going for an epic skin (while maintaining professionalism)."

### What v1.2 designs ARE good for

The v1.2 chromas remain useful as:
- **Starting points** — the new epic skins can fork from the best elements of A/B/C rather than starting from v1.1
- **Baseline comparison** — "does this epic skin look clearly different from the chromas?"
- **Copy source** — the snappier German wording can be reused

## v1.3 Goal

**Produce 3 structurally distinct ("epic skin") design explorations, review them with the user, then synthesize feedback into Design D (Claude's autonomous vision).**

The purpose of the 3 explorations is to create **discussion surface** — give the user enough visual variety to form opinions and preferences. Design D is the real deliverable: Claude's best synthesis of everything learned.

### The "Epic Skin" Standard

An epic skin is NOT just different colors/fonts on the same skeleton. It must feel like a **different product** while serving the same content and conversion goals.

**Each design MUST differ from the others in at least 3 of these structural dimensions:**

1. **Section ordering / content flow** — Different homepage section sequence. Not all designs should go hero → gate → benefits → pricing → CTA. One might lead with social proof, another with a cost comparison, another with the "how it works" flow.

2. **Hero composition** — Different spatial arrangements:
   - Asymmetric split (content 60% / visual 40%)
   - Full-bleed immersive (background covers viewport, content layered)
   - Stacked editorial (large headline + layered visual elements, overlapping cards or floating badges creating a "scene")
   - NOT all centered h1 + subtitle + CTA button(s)

3. **Navigation pattern** — At least one design should break the "sticky top bar" convention:
   - Side navigation (left rail)
   - Floating pill/FAB navigation
   - Bottom navigation (mobile-native)
   - Minimal header with expandable mega-menu
   - NOT all "sticky bar, logo left, links right, hamburger mobile"

4. **Content container approach** — Already varied in v1.2 (lines vs bands vs cards). Keep this variety but pair it with different structural layouts.

5. **Information density / rhythm** — Mix of:
   - Dense magazine-style (lots of content visible at once, multi-column)
   - Airy minimal (one idea per viewport, scroll-driven)
   - Focused storytelling (sequential narrative flow, each section builds on previous)

6. **Unique visual signature element** — Each design needs one distinctive visual element that only it uses:
   - Custom SVG illustrations or icons
   - Distinctive background pattern or texture
   - Unique typographic treatment (e.g., oversized numbers, pull quotes, highlighted words)
   - Decorative element that carries throughout pages (e.g., a wave shape, diagonal cuts, organic blobs)
   - NOT just "different color gradients"

### What "structural distinctness" does NOT mean

- It does NOT mean sacrificing usability for novelty
- It does NOT mean inventing new UX patterns that confuse users
- It does NOT mean the designs need to be experimental or "artsy"
- All designs must still be **professional and conversion-effective**
- Think: 3 different architecture firms designing the same house brief — same rooms, same requirements, completely different buildings

## Shared Constraints (carried from v1.2)

These constraints from `20-DESIGN-DIRECTIONS.md` still apply to ALL v1.3 designs:

1. **Tech stack: HTML + Tailwind CSS v4 only.** No SPA, no CMS, no server runtime.
2. **Tailwind v4 `@theme` syntax** for color/font tokens.
3. **Google Fonts CDN only.** Must support full German character set.
4. **8 pages fixed.** index, preise, fahrzeuge, geschaeftskunden, ueber-uns, mitglied-werden, impressum, datenschutz.
5. **Phone CTA only: 07473-922202.** No email, no forms.
6. **Membership gate communication required.** Clearly communicate membership model early.
7. **Content accuracy — no invented facts.** Snappier wording from existing verified content only.
8. **Zweitwagen persona primary (Simone).** Homepage hero speaks to her use case.
9. **Responsive: 375px / 768px / 1280px+.** Mobile-first.
10. **Copyright: no student project images.** CSS/SVG decorations are safe.
11. **German language, Sie-Ansprache.** Sachlich + freundlich.
12. **Legal pages must remain intact.** Impressum and datenschutz accommodate long-form text.
13. **Pricing data via pricing.json + pricing.js pattern.** No hardcoded prices.
14. **MapLibre map on fahrzeuge.html.** 420-520px tall map container.
15. **Tailwind v4 `@theme` block replaces all tokens.** Each design has its own theme.

### Additional v1.3 constraints

16. **Each design direction must include a "Structural Signature" section** that explicitly states: (a) homepage section ordering, (b) hero composition type, (c) nav pattern, (d) unique visual signature element, (e) how it differs structurally from the other two.

17. **Copy MUST vary across designs.** Same facts, different emphasis and ordering. One design might lead with cost savings, another with convenience, another with community/personal touch. The copy strategy is part of the structural identity.

18. **No two designs may share the same hero composition type.** If A uses asymmetric split, B and C must use something else.

19. **The 3 epic skin designs live in parallel directories** (`site/epic/a/`, `site/epic/b/`, `site/epic/c/`) on the same branch. No branch switching or worktrees needed — agents commit only their own directory's files. Old chroma branches are preserved as reference.

## Phase Structure

### Phase 26: Epic Directions
**Goal:** Write 3 structurally distinct design direction specifications — each with a unique page skeleton, hero composition, nav pattern, content flow, and visual signature. This replaces Phase 20's `20-DESIGN-DIRECTIONS.md` with `26-EPIC-DIRECTIONS.md`.
**Depends on:** Nothing (first phase of v1.3; references v1.2 learnings)
**Success Criteria:**
  1. Three directions written, each with explicit "Structural Signature" section
  2. No two directions share the same hero composition type
  3. Each direction specifies different homepage section ordering
  4. Differentiation matrix shows at least 3 structural differences between each pair
  5. Each direction includes copy strategy (what content emphasis, what emotional arc)
  6. Document makes clear how each direction is an "epic skin" not a "chroma"

### Phase 27: Epic Skin A
**Goal:** A complete 8-page site on `design/a` branch — structurally distinct per Epic Direction A, with its own page skeleton, hero, nav, content flow, and visual signature. Refined through Playwright screenshot loops.
**Depends on:** Phase 26
**Success Criteria:**
  1. All 8 pages render correctly on `design/a` branch
  2. Homepage section ordering matches Epic Direction A specification (and differs from B and C)
  3. Hero composition is unique to this design (not shared with B or C)
  4. At least one page demonstrates a layout pattern not used in any v1.2 chroma
  5. Visual signature element (the distinctive "this is Design A" element) appears consistently across pages
  6. Copy emphasis/ordering differs from B and C — same facts, different storytelling
  7. Playwright screenshots at 375px, 768px, 1280px show no layout breaks
  8. Navigation pattern is functional and accessible

### Phase 28: Epic Skin B
**Goal:** Same as Phase 27 but for Epic Direction B on `design/b` branch.
**Depends on:** Phase 26 (can run parallel to Phase 27)
**Success Criteria:** Mirror Phase 27 criteria with "B" substituted.

### Phase 29: Epic Skin C
**Goal:** Same as Phase 27 but for Epic Direction C on `design/c` branch.
**Depends on:** Phase 26 (can run parallel to Phases 27-28)
**Success Criteria:** Mirror Phase 27 criteria with "C" substituted.

### Phase 30: Epic Review
**Goal:** User reviews all 3 epic skins side-by-side. Feedback is captured as a structured document that feeds directly into Design D.
**Depends on:** Phases 27, 28, 29
**Success Criteria:**
  1. All three epic skins viewable side-by-side (live branches or screenshots)
  2. User has evaluated structural distinctness, conversion effectiveness, and aesthetic preference
  3. Specific feedback captured per design: what works, what doesn't, what to keep for D
  4. Design D brief written incorporating review feedback
  5. Review verdict documented (which elements from which designs to carry forward)

### Phase 31: Design D — Claude's Synthesis
**Goal:** Claude's autonomous design vision on `design/d` branch — synthesizes the best structural elements from epic skins A/B/C based on user review feedback. Must use the frontend-design skill. This is the intended winner.
**Depends on:** Phase 30
**Success Criteria:**
  1. All 8 pages render correctly on `design/d`
  2. Design incorporates specific feedback from Phase 30 review
  3. Structural elements deliberately chosen from review (e.g., "A's hero + C's nav + B's content flow")
  4. Cohesive visual identity — not a Frankenstein of parts but a unified synthesis
  5. Frontend-design skill used for implementation
  6. Playwright screenshots clean at all breakpoints

## Requirements to Add

### Structural Identity (new for v1.3)

- **STRUCT-01**: Each design direction specifies a unique page skeleton (section ordering, hero type, nav pattern)
- **STRUCT-02**: No two designs share the same hero composition type
- **STRUCT-03**: Each design has a unique visual signature element that appears consistently across pages
- **STRUCT-04**: Copy strategy varies per design (same facts, different emphasis and emotional arc)
- **STRUCT-05**: Differentiation matrix proves at least 3 structural differences between each design pair

### Review & Synthesis (new for v1.3)

- **SYNTH-01**: Epic review captures per-design feedback (what works, what doesn't, what to keep)
- **SYNTH-02**: Design D brief incorporates specific review feedback before implementation
- **SYNTH-03**: Design D's structural choices are traceable to review feedback
